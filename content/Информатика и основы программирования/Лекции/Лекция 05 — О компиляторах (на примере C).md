## 1. Программа, код и вычислитель

**Компилятор** — транслятор, преобразующий программу из одного представления в другое, предназначенное для выполнения некоторым вычислителем. В типичном случае это перевод исходного языка в машинный код (часто через промежуточные представления).

**Код** — запись программы для некоторого вычислителя. **Вычислитель** — система, исполняющая предусмотренные для неё инструкции: физический процессор или виртуальная машина.

Виды представлений:

| Представление | Смысл |
|---|---|
| **Машинный код** | Инструкции конкретной архитектуры процессора. |
| **Байт-код** | Инструкции виртуального вычислителя, например JVM (Java Virtual Machine — виртуальная машина Java). |
| **Псевдокод** | Условная запись действий, обычно не предназначенная для непосредственного выполнения. |
| **Микрокод** | Низкоуровневое представление, используемое в реализации некоторых процессоров. |

**Исполняемый код не обязательно является машинным кодом:** байт-код можно исполнить с помощью соответствующей виртуальной машины. Исполняемость определяется средой исполнения.

**Алгоритм и программа** — не строгие синонимы. В принятом на лекции упрощённом различении алгоритм решает поставленную задачу за конечное число шагов, тогда как программа может описывать и непрерывную обработку событий (например, сервер). *Термин «алгоритм» в теории вычислений имеет и более широкие трактовки.*

Архитектуры вычислителей различаются:

- **RISC (Reduced Instruction Set Computer)** — подход с относительно простым набором машинных команд (примеры: ARM, RISC-V).
- **CISC (Complex Instruction Set Computer)** — подход с более сложными машинными командами (пример: x86).
- **VLIW (Very Long Instruction Word)** — архитектурный подход, в котором несколько операций явно объединяются в длинную инструкцию.
- **SIMD (Single Instruction, Multiple Data)** — *принцип* обработки нескольких элементов данных одной инструкцией; это не название одной конкретной команды. SIMD может поддерживаться в различных архитектурах.

## 2. Формальные языки и трансляция

Понятия из теории формальных языков:

- **Алфавит** $\Sigma$ — конечное множество символов, например $\Sigma=\{0,1\}$.
- **Цепочка** — конечная последовательность символов алфавита, например `10101`; существует и пустая цепочка $\varepsilon$.
- **Язык** $L$ — множество цепочек над алфавитом.

Пример: язык цепочек над $\{0,1\}$, заканчивающихся на `1`, содержит `1`, `01`, `101`, но не `100`.

**Зачем это компилятору:** исходный текст — цепочка символов, и компилятор должен определить, соответствует ли запись правилам языка. Например, `int x = 5;` — корректная конструкция C, а `int = x 5;` — нет.

**Трансляция** — перевод из одного формального языка в другой. В простейшей модели это отображение $T:L_1\to L_2$; в общем случае можно рассматривать и отношение, допускающее несколько вариантов перевода.

**Транслятор** — алгоритм, осуществляющий такой перевод. Компилятор и ассемблер — примеры трансляторов.

**Синтаксически управляемая трансляция** связывает правила грамматики с действиями по генерации результата. Пример правила из лекции:

$$
E\to E_1+T,\qquad
\operatorname{code}(E)=\operatorname{code}(E_1)\mathbin{++}\operatorname{code}(T)\mathbin{++}\text{ADD}.
$$

Здесь $E$ — целое выражение, $E_1$ и $T$ — его части, а $++$ — соединение последовательностей инструкций. Для `2 + 3` можно сгенерировать условный стековый код `PUSH 2; PUSH 3; ADD`. Подход используется в построении компиляторов; упомянутые инструменты — **GNU Bison** и **ANTLR**.

*Дополнение.* В алфавите исходного текста отдельными символами будут, например, `f`, `o`, `r`; после лексического анализа `for` рассматривается как один **токен** (ключевое слово). В лекции допускается и более высокий уровень абстракции, когда токены рассматривают как символы формального языка.

## 3. Четыре этапа сборки программы

В лекции различаются **этапы (stages)** всего конвейера сборки и **фазы (phases)** внутри собственно компилятора.

| Этап | Что делает | Типичный результат |
|---|---|---|
| **1. Препроцессор** (*preprocessor*, флаг `-E`) | Обрабатывает `#include`, `#define`, `#if`, `#ifdef`, выполняет макроподстановки. | `main.c` → `main.i` |
| **2. Компилятор в узком смысле** (*compiler*, флаг `-S`) | Анализирует C-код, оптимизирует и генерирует язык ассемблера. | `main.i` → `main.s` |
| **3. Ассемблер** (*assembler*, флаг `-c`) | Переводит мнемоники ассемблера в машинный код и объектный файл. | `main.s` → `main.o` |
| **4. Линкер** (*linker, link editor*, без флага) | Связывает объектные модули и библиотеки, формирует исполняемый модуль. | `main.o` + библиотеки → исполняемый файл |

**Компиляция в широком смысле** — весь процесс сборки. **Компилятор в узком смысле** — второй этап. Команда `gcc` (из **GCC — GNU Compiler Collection**, набора компиляторов GNU) обычно выступает **драйвером**: организует вызов инструментов всех этапов. Для C внутренний компилятор GCC называется `cc1`, для C++ — `cc1plus` (конкретная цепочка и исполняемые программы зависят от окружения).

Препроцессор **включает заголовок** с объявлениями, а линкер **связывает вызовы с реализациями**. Эти действия не следует смешивать:

```c
#include <stdio.h>  // Объявление printf, среди прочего

int main(void) {
    printf("Hello!\n");
    return 0;
}
```

В типичном случае реализация `printf` находится в библиотеке C, а не в `stdio.h`.

**Как увидеть этапы (GCC):**

```bash
gcc -v main.c -o main          # Показать вызываемые инструменты
gcc -save-temps main.c -o main # Сохранить промежуточные файлы
```

*Дополнение для macOS (Clang):*

```bash
clang -E main.c -o main.i      # Препроцессинг
clang -S main.i -o main.s      # Генерация ассемблера
clang -c main.s -o main.o      # Объектный файл
clang main.o -o main           # Линковка
```

Файлы `.i`, `.s`, `.o` иллюстрируют этапы, но внутренние промежуточные файлы не обязаны сохраняться при обычной сборке. Формат объектных и исполняемых файлов зависит от ОС (например, **ELF — Executable and Linkable Format** в Linux, **Mach-O — Mach Object** в macOS, **PE — Portable Executable** в Windows).

## 4. Пять фаз внутри компилятора

Рассмотрим `int x = 2 + 3;`.

1. **Лексический анализ (lexing, scanning, tokenization).** Разбивает входной текст на **токены**: `int`, `x`, `=`, `2`, `+`, `3`, `;`.
2. **Синтаксический анализ (parsing).** Проверяет структуру по грамматике и строит представление, отражающее вложенность выражений и операторов.
3. **Семантический анализ (semantic analysis).** Проверяет допустимость конструкций: существование имён, типы и операции над ними; дополняет представление программы информацией.
4. **Оптимизация (optimization).** Преобразует программу в эквивалентную по наблюдаемому поведению, но более эффективную по заданному критерию.
5. **Кодогенерация (code generation).** Создаёт код для целевой архитектуры, например ассемблерный текст.

**Синтаксис** — допустима ли форма записи: `int x = 2 + ;` — синтаксическая ошибка (нет второго операнда). **Семантика** — допустим ли смысл конструкции: после `int x = 5;` запись `x();` синтаксически напоминает вызов, но семантически неверна — `x` не функция.

| Место ошибки | Пример |
|---|---|
| Препроцессинг | Не найден файл в `#include`. |
| Синтаксический анализ | Пропущен операнд или `;`. |
| Семантический анализ | Несовместимые типы или вызов числа как функции. |
| Линковка | Функция объявлена и вызвана, но определение не найдено среди подключённых модулей и библиотек. |

Фазы — **логическое разделение**. Реальные компиляторы могут использовать больше внутренних представлений и проходов, а некоторые действия совмещать.

## 5. Структуры данных компилятора

### 5.1. Дерево разбора и AST

**Parse tree (дерево разбора)** отражает применение правил грамматики. **AST (Abstract Syntax Tree — абстрактное синтаксическое дерево)** сохраняет смысловые конструкции без лишних синтаксических деталей.

Для выражения `2 + 3 * 4` упрощённое AST:

```text
      +
     / \
    2   *
       / \
      3   4
```

Корень `+` — последняя выполняемая операция, умножение образует правое поддерево. Для `(2 + 3) * 4` корнем был бы `*`.

Дерево нужно для анализа структуры, проверки типов, оптимизаций и кодогенерации.

### 5.2. Таблица символов (symbol table)

Хранит сведения об именах: объявления, типы, области видимости и другую информацию. Например, для `int age; double price;` таблица содержит записи `age → int`, `price → double`.

Для быстрого поиска часто используют **хеш-таблицу (hash table)**, обеспечивающую в среднем поиск за $O(1)$ при подходящих условиях.

### 5.3. CFG — граф потока управления

**CFG (Control Flow Graph — граф потока управления)** — ориентированный граф возможных путей выполнения программы. Его вершины обычно представляют **базовые блоки** (последовательности инструкций без внутренних переходов), рёбра — возможные переходы управления.

```text
        [проверка x > 0]
           /       \
         да        нет
         /           \
     [y = 1]       [y = 2]
         \           /
          [использовать y]
```

`if` даёт ветвление, `while` — переход назад к проверке условия. CFG помогает искать недостижимый код, анализировать пути выполнения и оптимизировать программу. **Граф потока данных (data-flow graph)** — иная структура: он показывает зависимости между данными и вычислениями, а не только возможный порядок выполнения.

## 6. Оптимизации

**Оптимизация** сохраняет допустимое наблюдаемое поведение программы, улучшая выбранную метрику: **скорость, размер кода или энергопотребление**. Эти цели могут конфликтовать. В лекции **функционал** — правило, ставящее программе в соответствие числовую оценку выбранной метрики.

### 6.1. Платформенно-независимые

Не требуют знания конкретного набора инструкций процессора.

| Название | Смысл | Упрощённый пример |
|---|---|---|
| **Constant folding** — свёртка констант | Вычислить известное выражение при компиляции. | `2 * 10` → `20` |
| **Constant propagation** — распространение констант | Подставить известное значение переменной. | `a = 5; b = a + 1` → использование `5` вместо `a` |
| **CSE (Common Subexpression Elimination)** — устранение общих подвыражений | Не пересчитывать одно выражение повторно, если аргументы не изменились. | Два вычисления `a*b` → одно общее |
| **DCE (Dead Code Elimination)** — удаление мёртвого кода | Убрать результат, который никогда не используется. | `x=5; x=10; print(x)` → первое присваивание лишнее |
| **Loop unrolling** — разворачивание цикла | Уменьшить затраты на управление циклом за счёт повторения тела. | 3 итерации → 3 последовательных операции |

Преобразования выполняются только тогда, когда компилятор может обосновать их корректность; например, нельзя бездумно удалять действия с наблюдаемыми побочными эффектами.

### 6.2. Платформенно-зависимые

Учитывают архитектуру и особенности целевого процессора:

- **Register allocation — распределение регистров.** Регистров ограниченное число; компилятор решает, какие значения держать в быстрых регистрах, а какие временно хранить в памяти. Один из методов связан с раскраской графа конфликтов.
- **Instruction selection — выбор инструкций.** Компилятор подбирает конкретные машинные команды из доступного процессору набора.
- **Auto-vectorization — автовекторизация.** Компилятор **автоматически** заменяет подходящие операции над отдельными элементами на векторные операции с использованием SIMD. Цикл не обязательно исчезает: он может, например, обрабатывать по 4 элемента за итерацию вместо 1.

**SIMD (Single Instruction, Multiple Data)** — принцип «одна инструкция над несколькими элементами данных». **SIMD-инструкция** — конкретная команда процессора, реализующая этот принцип. У разных архитектур — разные векторные расширения (например, SSE — *Streaming SIMD Extensions*, AVX — *Advanced Vector Extensions* у x86; NEON у ARM).

Пример: скалярный цикл `c[i] = a[i] + b[i]` потенциально может быть преобразован в векторные сложения нескольких пар элементов за раз. **«Авто» означает, что программист написал обычный цикл, а решение использовать векторные инструкции принял компилятор.**

### 6.3. Уровни оптимизации и предупреждения

| Флаг GCC/Clang | Назначение |
|---|---|
| `-O0` | Основные оптимизации отключены, удобно для отладки. |
| `-O1` | Базовые оптимизации. |
| `-O2` | Более широкий набор оптимизаций. |
| `-O3` | Более агрессивные оптимизации ради производительности. |
| `-Os` | Оптимизация с акцентом на уменьшение размера. |
| `-Wall` | Основные предупреждения компилятора. |
| `-Wextra` | Дополнительные предупреждения. |
| `-pedantic` | Диагностика нарушений требований выбранного стандарта языка. |

Рекомендуемый в лекции минимум для C:

```bash
gcc -O1 -Wall -Wextra -pedantic main.c -o main
```

Для просмотра результатов разных оптимизаций — [Compiler Explorer](https://godbolt.org/z/5K8GWfKn7). Разные уровни `-O` и целевые архитектуры могут давать существенно разный машинный код.

**Статический анализ (static analysis)** исследует программу **без её выполнения** (например, предупреждения компилятора). **Динамический анализ (dynamic analysis)** исследует программу **во время выполнения** (например, санитайзеры и профилировщики). Оба подхода помогают обнаруживать ошибки и проблемы производительности.

## 7. Объектные файлы, линкер и библиотеки

**Единица трансляции** в C — исходный файл после препроцессинга с включёнными заголовками. Результат его компиляции и ассемблирования — **объектный модуль** (`.o`, `.obj`): машинный код, данные и вспомогательные сведения (символы, информация для отладки, связывания и т. д.). Сам по себе он обычно ещё не готов к самостоятельному запуску.

**Линкер (linker, link editor — редактор связей)** объединяет объектные модули и разрешает ссылки на внешние функции и данные.

```c
// main.c
int add(int, int);         // объявление
int main(void) { return add(2, 3); }
```

```c
// math.c
int add(int a, int b) { return a + b; } // определение
```

`main.c` и `math.c` компилируются отдельно в `main.o` и `math.o`, затем линкер связывает вызов `add()` с определением из `math.o`.

**Заголовок (`.h`) ≠ бинарная библиотека.** В типичном случае заголовок содержит объявления, необходимые компилятору, а библиотека — реализацию. Препроцессор включит `math.h`, но если реализация `add` находится в `math.o`, этот объектный файл всё равно понадобится при линковке. *Исключение:* существуют **header-only libraries**, содержащие реализации прямо в заголовках.

**Статическая библиотека** (часто `.a` в Unix, `.lib` в Windows) — архив объектных модулей; нужный код включается при линковке в результирующий исполняемый файл.

**Динамическая библиотека** (Linux: `.so` — *shared object*; Windows: `.dll` — *dynamic-link library*; macOS: `.dylib`) подключается механизмами динамической загрузки при запуске или во время выполнения. Один код библиотеки может использоваться несколькими процессами без отдельного копирования в каждый исполняемый файл.

**Почему `main()` не обязательно первая выполняемая функция.** ОС знает формат исполняемого модуля и его точку входа, а не правило языка C про `main`. Стартовый код среды выполнения C (**CRT — C Runtime**) готовит окружение, вызывает `main`, затем организует завершение программы. В Linux типичная точка входа — `_start`.

## 8. Front-end, Middle-end, Back-end и LLVM

Это **три части компилятора в узком смысле**, расположенные внутри второго этапа общего конвейера сборки.

| Часть | Назначение | Зависимость |
|---|---|---|
| **Front-end** — входная часть | Лексический, синтаксический и семантический анализ. | От **исходного языка** (C, Rust и т. д.). |
| **Middle-end** — промежуточная часть | Оптимизации над внутренним представлением программы. | В значительной мере независима от исходного языка. |
| **Back-end** — выходная часть | Генерация кода и оптимизации под конкретную архитектуру. | От **целевой платформы** (ARM, x86-64, RISC-V и т. д.). |

**IR (Intermediate Representation — промежуточное представление)** — внутренний формат программы между анализом исходного языка и генерацией конечного кода.

**LLVM** — инфраструктура для создания компиляторов, включающая средства работы с **LLVM IR**, оптимизации и генерации машинного кода для разных архитектур. Исторически аббревиатура означала *Low Level Virtual Machine*, но сегодня LLVM — самостоятельное название проекта. **Clang** — front-end/компилятор для C и C++, использующий LLVM.

Принцип переиспользования:

```text
Front-end для C ─────┐
                     ├→ LLVM IR → общие оптимизации → Back-end ARM → машинный код ARM
Front-end для Rust ──┘                           └→ Back-end x86 → машинный код x86
```

Если front-end нового языка умеет генерировать LLVM IR, он может использовать уже существующие оптимизации и back-end LLVM: необязательно писать всё самостоятельно.

**Различие уровней:** `gcc` как драйвер управляет конвейером; *front-end / middle-end / back-end* описывают внутреннюю архитектуру собственно компилятора. Общая вложенность показана на SVG-схеме в начале конспекта.

## 9. Интерпретация, AOT и JIT

**Интерпретатор** выполняет программу или её промежуточное представление, вместо предварительного получения всего нужного машинного кода отдельной сборкой. Реальные среды могут совмещать компиляцию и интерпретацию: **CPython** обычно компилирует исходный Python в байт-код, а затем интерпретирует его.

**AOT (Ahead-of-Time Compilation — предварительная компиляция)** — создание машинного кода **до запуска** программы; типичный пример — обычная сборка C.

**JIT (Just-in-Time Compilation — компиляция во время выполнения)** — генерация машинного кода **в ходе работы** программы. Например, JVM может сначала интерпретировать байт-код, обнаружить часто выполняемую («горячую») функцию, скомпилировать её и далее использовать машинный код вместо повторной интерпретации каждой инструкции.

**Зачем JIT:** тратить ресурсы на компиляцию прежде всего там, где стоимость компиляции может окупиться ускорением многократного выполнения. JIT также может использовать статистику именно текущего запуска и особенности конкретного процессора. Не всякий JIT обязан следовать этой схеме в точности.

| | AOT | JIT |
|---|---|---|
| **Когда** | До запуска. | Во время выполнения. |
| **Данные о реальном выполнении** | Обычно отсутствуют, но возможен PGO. | Могут собираться на ходу. |
| **Цена** | Время компиляции до запуска. | Время и ресурсы на компиляцию во время работы. |

**Интерпретируемый / компилируемый язык** — условные выражения: способы выполнения зависят от реализации, а не только от языка.

## 10. Bootstrapping и кросс-компиляция

**Bootstrapping — раскрутка компилятора.** Если новый компилятор C написан на C, для получения его первой исполняемой версии можно использовать **уже работающий** компилятор C (например, GCC). После этого новый компилятор может собирать собственные исходники, если поддерживает необходимые возможности языка. Первые компиляторы исторически могли писать на ассемблере или другом доступном языке.

**Cross-compilation — кросс-компиляция:** компилятор работает на одной платформе, но создаёт код для другой; например, сборка на ARM-машине для x86-64.

При **сборке самого компилятора** различают:

- **Build** — платформа, на которой компилятор **собирается**.
- **Host** — платформа, на которой собранный компилятор **будет запускаться**.
- **Target** — платформа, **для которой он будет генерировать код**.

В нативной ситуации: `Build = Host = Target`. В распространённом случае кросс-компилятора: `Build = Host ≠ Target`. **Canadian Cross — канадская сборка**: все три различны, например компилятор собирается на Linux, запускается на Windows и выдаёт код для ARM.

## 11. Доверие к компилятору

Работа Кена Томпсона **«Reflections on Trusting Trust» (1984)** показывает проблему: чистые исходники программы не гарантируют чистый исполняемый файл, если **сам компилятор** вредоносен.

Пример из лекции: заражённый компилятор незаметно добавляет обход проверки пароля в исполняемую программу `login`. Он также способен внедрить собственную вредоносную логику в **новый компилятор**, собираемый из чистых исходников. Поэтому пересборка заражённым компилятором сама по себе проблему не устраняет.

Вывод: доверять нужно не только исходному коду программы, но и инструментам её сборки. *Дополнение:* для проверки соответствия исходников и компилятора существуют подходы вроде **DDC (Diverse Double-Compiling — разнородная двойная компиляция)**.

## 12. Дополнительные возможности оптимизации

### 12.1. Инкрементальная сборка и линковка

**Incremental linking — инкрементальная линковка** использует информацию от предыдущей сборки и по возможности переделывает только изменившиеся части вместо полной пересборки.

### 12.2. LTO — Link-Time Optimization

**LTO (Link-Time Optimization — оптимизация во время линковки)** даёт возможность оптимизировать код **через границы отдельных единиц трансляции**. Для этого объектные файлы могут содержать не только машинный код, но и промежуточное представление.

Например, `main.c` вызывает `square(5)`, а реализация `square(x) { return x*x; }` находится в `math.c`. Без информации о теле внешней функции компилятору сложнее оптимизировать вызов. При LTO можно встроить её код (**inlining — встраивание функции**) и потенциально свернуть `5*5` до `25`.

**IPA / IPO (Interprocedural Analysis / Interprocedural Optimization)** — межпроцедурный анализ и оптимизация. **WPO (Whole-Program Optimization)** — оптимизация программы в целом, насколько доступен её код.

### 12.3. PGO — Profile-Guided Optimization

**PGO (Profile-Guided Optimization — оптимизация на основе профиля выполнения)** использует статистику типичных запусков программы: какие ветви и функции выполняются чаще.

Типичная схема:

1. Собрать версию, фиксирующую профиль выполнения.
2. Запустить на характерных данных.
3. Повторно собрать программу с использованием профиля.

**Главное различие:** LTO даёт оптимизатору **больше видимого кода**, PGO — **данные о том, как код реально выполнялся**. Их можно сочетать; например, PGO помогает решить, какие функции выгоднее встраивать, а LTO делает доступным их код из других модулей.

## 13. Смешанные вычисления и проекции Футамуры — Ершова

**Partial Evaluation — частичное вычисление; «смешанные вычисления»** в терминологии лекции. Это метод, позволяющий выполнить часть вычислений заранее, когда некоторые входные данные программы уже известны.

**Mix / Spec (specializer — специализатор)** — программа, которая принимает другую программу и заранее известный аргумент, а затем создаёт специализированную версию этой программы.

Если есть функция $F(a,b)$, то $\operatorname{Mix}(F,a)$ создаёт новую функцию $G$, у которой первый аргумент уже зафиксирован:

$$
G(b)=F(a,b).
$$

При этом специализатор может заранее выполнить вычисления, зависящие только от известного аргумента.

```python
# Исходная функция
def f(x, y):
    return x * x + y

# Заранее известно x = 10;
# специализатор может получить:
def f10(y):
    return 100 + y
```

На этом принципе основаны три проекции Футамуры — Ершова.

### Первая проекция — получение исполняемой программы

Пусть интерпретатор выполняет программу $P$ на входных данных $D$ и возвращает результат $R$:

$$
\operatorname{Interp}(P,D)=R.
$$

Специализируем интерпретатор, **фиксируя в нём конкретную программу $P$**:

$$
\boxed{\operatorname{Mix}(\operatorname{Interp},P)=P'}.
$$

Полученная программа $P'$ уже предназначена для выполнения конкретной $P$, принимает подходящие данные $D$ и может не тратить время на универсальный разбор и интерпретацию $P$:

$$
P'(D)=\operatorname{Interp}(P,D)=R.
$$

**Результат:** исполняемая версия конкретной программы — аналог результата компиляции.

### Вторая проекция — получение компилятора

В первой проекции используется один интерпретатор, а меняется программа:

```text
Mix(Interp, P₁) → P₁'
Mix(Interp, P₂) → P₂'
Mix(Interp, P₃) → P₃'
```

Чтобы не использовать универсальный Mix с одним и тем же интерпретатором каждый раз, можно **специализировать сам Mix, зафиксировав в нём Interp**:

$$
\boxed{\operatorname{Mix}(\operatorname{Mix},\operatorname{Interp})=C}.
$$

Внешний Mix выполняет специализацию; внутренний Mix — программа, которую специализируют; Interp — значение, фиксируемое как первый аргумент внутреннего Mix. Полученная программа $C$ удовлетворяет:

$$
C(P)=\operatorname{Mix}(\operatorname{Interp},P)=P'.
$$

То есть $C$ принимает разные исходные программы $P$ и создаёт их исполняемые версии $P'$.

**Результат:** компилятор для языка, который понимает зафиксированный интерпретатор.

### Третья проекция — генератор компиляторов

Во второй проекции получаются компиляторы для разных интерпретаторов:

```text
Mix(Mix, Interp₁) → C₁
Mix(Mix, Interp₂) → C₂
Mix(Mix, Interp₃) → C₃
```

Первый аргумент всегда Mix, а меняется интерпретатор. Поэтому Mix специализируют ещё раз, фиксируя его первый аргумент равным самому Mix:

$$
\boxed{\operatorname{Mix}(\operatorname{Mix},\operatorname{Mix})=G}.
$$

Полученная программа $G$ принимает только интерпретатор:

$$
G(\operatorname{Interp})
=\operatorname{Mix}(\operatorname{Mix},\operatorname{Interp})
=C.
$$

Правая часть — уже известная вторая проекция, создающая компилятор.

**Результат:** генератор компиляторов — программа, которая получает интерпретатор некоторого языка и создаёт соответствующий компилятор.

### Итог

| Проекция | Что фиксируем | Что получаем |
|---:|---|---|
| 1 | Программу в интерпретаторе | Исполняемую программу |
| 2 | Интерпретатор в специализаторе | Компилятор |
| 3 | Сам Mix в специализаторе | Генератор компиляторов |

Во всех трёх случаях применяется один механизм: специализация программы с фиксацией заранее известного аргумента.

> [!note] Оговорка
> Это теоретические конструкции. Для второй и третьей проекций нужен специализатор, способный работать с собственным программным представлением. Записи равенств описывают поведение полученных программ, а не обязательное совпадение их внутреннего кода.


## 14. Практический итог

- При ошибке сборки определять её **этап**: препроцессинг, анализ исходного кода или линковка.
- Включать **предупреждения компилятора** (`-Wall -Wextra`, при необходимости `-pedantic`) и разумный уровень оптимизации.
- Понимать разницу между **заголовком, объектным файлом, статической и динамической библиотекой**.
- При необходимости смотреть сгенерированный ассемблер и влияние опций оптимизации (Compiler Explorer; `objdump` в Linux, `otool` в macOS).
