## Форматирование и code style

**Code style** — договорённости о внешнем виде кода: имена, отступы, скобки, длина строк.

**Форматтер** автоматически приводит код к единому виду, **не меняя его смысла**.

Главное — не «лучший» стиль, а **единый стиль в проекте**.

Основные принципы:
- понятные имена;
- единые отступы;
- аккуратные пробелы;
- разумная длина строк;
- разделение смысловых блоков;
- одно действие — одна строка.

Форматтеры:
- Python — `ruff`, `black`;
- C — `clang-format`;
- Kotlin — `ktlint`;
- Rust — `rustfmt`;
- Pascal — `ptop`, Lazarus formatter.

## Анализаторы

### Статические
Работают **до запуска программы**.

Находят:
- проблемы стиля;
- неиспользуемые переменные;
- сомнительные конструкции;
- ошибки типов.

Примеры: линтеры, компиляторы, type checking.

**Типы — это статический анализ:** например, если функция ожидает `int`, а получает строку, такую ошибку можно обнаружить до запуска.

Статические проверки дешевле, но ограничены доступной без запуска информацией.

### Динамические
Работают **во время выполнения**.

Примеры:
- **AddressSanitizer** — проблемы памяти;
- **coverage** — какие строки реально выполнились под тестами;
- **profiler** — где программа тратит время и память.

Динамические проверки дороже, но могут находить более сложные проблемы.

Статические анализаторы:
- Python — `ruff`, `mypy`, `pyright`;
- C — `gcc -Wall`, `clang-tidy`, `cppcheck`;
- Kotlin — `detekt`, `ktlint`;
- Rust — `cargo clippy`, borrow checker;
- Pascal — FPC warnings, Lazarus IDE.

## Тестирование

Ошибки неизбежны, поэтому задача тестирования — уменьшать их количество и влияние.

### Виды тестов

**Функциональные** — проверяют, что программа делает то, что должна.

**Нефункциональные** — проверяют другие свойства:
- производительность;
- безопасность;
- удобство использования.

Это только один из возможных способов классификации.

### Уровни тестирования

- **Unit** — отдельные компоненты;
- **Integration** — взаимодействие компонентов;
- **End-to-end (E2E)** — система целиком, как её видит пользователь.

```text
        E2E
    Integration
       Unit
```

Чем выше уровень, тем тесты обычно сложнее и дороже запускать.  
Чем ниже — тем быстрее и проще.

Хороший набор тестов сочетает разные уровни.

## Unit-тесты

Unit-тесты:
- проверяют одну компоненту;
- должны быть быстрыми;
- проверяют разные, особенно краевые, случаи;
- их должно быть много;
- помогают при рефакторинге;
- служат документацией ожидаемого поведения;
- помогают улучшать архитектуру.

**Unit-тесты не доказывают отсутствие ошибок — они делают ошибки дешевле.**

Фреймворки:
- Python — `pytest`, `unittest`;
- C — `CTest`, `Check`, `GoogleTest`;
- Kotlin — `JUnit`, `kotest`;
- Rust — `cargo test`.

## TDD

**TDD (Test-Driven Development)** — тесты пишутся до реализации.

Цикл:

```text
Красный → Зелёный → Рефакторинг
```

1. **Красный** — пишется тест нужного поведения, он падает.
2. **Зелёный** — пишется минимум кода, чтобы тест прошёл.
3. **Рефакторинг** — код улучшается, тест остаётся зелёным.

TDD:
- формулирует задачу через ожидаемое поведение;
- заставляет думать о поведении снаружи, а не о внутренней реализации;
- даёт fail-fast при поломках;
- превращает тесты в контракт поведения.

## IDE

IDE объединяет инструменты в одном месте:
- подсветка проблем;
- format-on-save;
- запуск тестов и анализаторов;
- фоновые проверки.

Это удобнее, чем запускать `ruff`, `mypy`, `pytest` и другие инструменты вручную по очереди.

## Continuous Integration (CI)

**CI** автоматически запускает сборку и проверки при изменениях, например на `push` или `pull request`.

Главная идея: те же проверки, что локально, но:
- на **чистой машине**;
- автоматически;
- без пропусков.

CI может запускать:
- форматирование;
- линтеры;
- анализаторы;
- тесты.

Примеры систем:
- GitHub Actions;
- GitLab CI;
- Jenkins;
- TeamCity.

**GitHub Actions — это один из инструментов CI, а не сам CI.**

При соответствующих настройках изменение не попадает в `main`, пока проверки не пройдены.

Принцип:

> `main` всегда зелёный.

---

## В эпоху ИИ

Чем больше кода генерируется автоматически, тем важнее автоматические проверки:
- тесты проверяют поведение;
- анализаторы быстро находят проблемы;
- CI проверяет изменения в чистом окружении.

TDD удобно использовать как способ формализовать требования через тесты.
