## `git diff`

```bash
git diff
```

Показывает изменения, которые есть в рабочей директории, но ещё не добавлены в staging.

```bash
git diff --staged
```

Показывает изменения, которые уже добавлены через `git add` и попадут в следующий коммит.

---

## Merge-конфликт

Если две ветки по-разному изменили одно и то же место, Git не может выбрать вариант автоматически.

После ручного исправления:

```bash
git add <file>
git merge --continue
```

`git add` здесь помечает конфликт как решённый.

Важно: после merge ветка-источник не исчезает автоматически.

## Граф истории

```bash
git log --graph --oneline --all
```

- `--graph` — рисует ветвление ASCII-линиями;
- `--oneline` — один коммит в одну строку;
- `--all` — показывает все ветки.

Граф удобнее читать снизу вверх.

```text
* = коммит
(HEAD -> page) = сейчас находимся в ветке page
(config) = ветка config указывает на этот коммит
```

Если граф слишком запутанный:

```bash
git log --graph --oneline --all --parents
```

Показывает ещё и родителей каждого коммита.

## `git commit --amend`

Исправляет последний коммит вместо создания нового.

```bash
git add <file>
git commit --amend
```

Было:

```text
A → B
```

После amend:

```text
A → B'
```

Хэш меняется, потому что создаётся новый коммит вместо старого.

---

## `git add -p`

```bash
git add -p <file>
```

Позволяет добавлять в staging не весь файл, а отдельные куски изменений (`hunk`).

Основное:

```text
y — добавить кусок
n — не добавлять
```

---

## Интерактивный rebase

```bash
git rebase -i config
```

Текущая ветка перебазируется на `config`, а `-i` открывает редактор со списком коммитов.

Пример:

```text
pick P1
pick P2
```

Если оставить так:

```text
config → P1' → P2'
```

Если сделать:

```text
pick P1
squash P2
```

то коммиты склеятся:

```text
config → P'
```

Основные команды редактора:

```text
pick    — оставить коммит
squash  — склеить с предыдущим
reword  — изменить сообщение
drop    — удалить коммит
```

Важно: `git rebase X` перебазирует именно текущую ветку поверх `X`.

## `git show`

```bash
git show
```

Показывает текущий коммит:
- хэш;
- автора;
- сообщение;
- diff.

Удобно проверить результат после `rebase`/`squash`.

---

## Push новой ветки

```bash
git push --set-upstream origin page
```

- отправляет локальную `page` в удалённый репозиторий `origin`;
- создаёт/использует `origin/page`;
- связывает локальную и удалённую ветки.

После этого обычно можно писать просто:

```bash
git push
```

---

## Pull Request

В практике PR делался:

```text
page → main
```

То есть изменения из удалённой `page` предлагаются для включения в `main`.

После `Squash and merge` изменения PR попадают в `main` одним новым коммитом.

---

## Синхронизация `main` после PR

После merge на GitHub удалённый `main` уже обновился, а локальный ещё нет.

```bash
git switch main
git pull
```

Теперь локальный `main` подтягивает изменения из `origin/main`.

---

## GitHub Pages

Для публикации страницы использовались:

```text
index.md
_config.yml
```

В Pages выбирается публикация из ветки `main` и корня репозитория.

---

## Схема всей практики

```text
создаём отдельные ветки
        ↓
merge + конфликт
        ↓
page с двумя коммитами
        ↓
rebase -i config
        ↓
squash в один коммит
        ↓
push page
        ↓
Pull Request page → main
        ↓
Squash and merge
        ↓
git pull в локальный main
```
