## 1. Переполнение буфера: исходная проблема (слайды 2–4)

```c
void func(char *name) {
    char buf[100];
    strcpy(buf, name);
    printf("Welcome %s\n", buf);
}
```

**Переполнение буфера (buffer overflow)** — запись за границы выделенной области памяти. `strcpy` копирует до `\0` **без проверки размера** `buf`; для `buf[100]` строка вместе с терминатором должна помещаться в 100 байт. Выход за границы — **неопределённое поведение (UB)**.

В показанной сборке `buf` расположен в **кадре стека**. Рядом находятся сохранённые регистры и **адрес возврата**: адрес инструкции, которую процессор должен выполнить после возвращения из функции. Повреждение адреса возврата способно изменить ход выполнения, а не только испортить строку.

**Из дизассемблирования:** `gcc vuln.c -o vuln -m32`; `objdump -d vuln`. В 32-битном варианте видно `push %ebp`, `mov %esp,%ebp`, выделение памяти `sub $0x84,%esp`, вызовы `strcpy@plt` и `printf@plt`, проверку защитного значения и `ret`. `-m32` выбирает 32-битный код, чтобы упростить демонстрацию адресов.

## 2. Как функции вызывают друг друга (слайды 5–15)

**Вызывающая функция (caller)** готовит аргументы и вызов, сохраняет нужное ей состояние, после вызова получает результат. **Вызываемая (callee)** принимает аргументы, выполняет работу, возвращает результат и восстанавливает регистры, за которые отвечает.

```c
int sum3(int a, int b, int c) { return a + b + c; }
int main(void) { int r = sum3(1, 2, 3); return r - 6; }
```

**Соглашение о вызовах (calling convention)** — договорённость caller и callee: где аргументы и результат, где адрес возврата, кто сохраняет регистры и кто очищает стек. **ABI — Application Binary Interface** (двоичный интерфейс приложений) включает соглашение о вызовах, но также определяет устройство данных и взаимодействие с системой. **API — Application Programming Interface** определяет доступные функции на уровне исходного кода.

### System V AMD64 ABI (Linux x86-64)

| Что | Где находится |
|---|---|
| Первые шесть целочисленных/указательных аргументов | `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9` |
| Последующие аргументы | На стеке; место готовит caller |
| Целочисленный результат | `rax` (для `int` — `eax`) |
| Результат с плавающей точкой | `xmm0` |
| Регистры caller-saved (могут измениться после вызова) | `rax`, `rcx`, `rdx`, `rsi`, `rdi`, `r8`–`r11` |
| Регистры callee-saved (callee должен восстановить при использовании) | `rbx`, `rbp`, `r12`–`r15` |

После вызова caller убирает выделенное им место под стековые аргументы. На лекции показан `sum7(1, 2, 3, 4, 5, 6, 7)`: седьмой аргумент передаётся на стеке. Соглашение также задаёт выравнивание стека (в примере — по 16 байт).

**Стековый кадр (stack frame)** — область стека, относящаяся к **одному вызову** функции. Может содержать локальные данные, сохранённые регистры, адрес возврата и служебную информацию. Стек на x86 растёт к **меньшим адресам**.

```asm
# Пролог (типичный пример)
push %rbp
mov  %rsp, %rbp
sub  $N, %rsp

# Эпилог
leave
ret
```

`rsp` — указатель вершины стека; `rbp` может быть базой кадра. `call` сохраняет адрес следующей инструкции и передаёт управление функции; `ret` возвращает управление по сохранённому адресу. Цепочка сохранённых `rbp` помогает отладке и **раскрутке стека (unwinding)**.

**Оптимизация:** в неоптимизированном примере `sum3` компилятор перекладывает параметры из регистров в память; при `-O2` вычисления могут остаться в регистрах, а отдельный кадр исчезнуть. `-fomit-frame-pointer` позволяет отказаться от `rbp` как базы кадра; `-fno-omit-frame-pointer` сохраняет его для удобства профилирования. **ABI остаётся обязательным независимо от оптимизаций.**

**Переменное число аргументов:** `printf("%d %s", 42, "hello")` определяет ожидаемые типы по строке формата; в C используется `va_list`. В системном ABI также передаётся информация о векторных аргументах (`al`). ❓ Фраза слайда «`va_list` — по сути указатель на стек» — учебное упрощение, не универсальное описание внутреннего устройства.

**Другие соглашения:** 32-битный `cdecl` передаёт аргументы справа налево через стек, очищает caller; `stdcall` очищает callee; на Windows x86-64 первые целочисленные аргументы идут через `rcx`, `rdx`, `r8`, `r9`; на Apple Silicon — через `x0`–`x7`. Нельзя смешивать несовместимые ABI.

**ABI шире вызова:** размеры типов, выравнивание, порядок байтов (*endianness*), имена символов C++ (*name mangling*), форматы ELF, системные вызовы, механизмы связывания и обработки исключений.

## 3. Динамические библиотеки: PLT и GOT (слайды 16–22)

При динамической линковке `printf`/`strcpy` находятся в `libc`, причём адрес загрузки библиотеки заранее неизвестен и может изменяться из-за ASLR. Поэтому в машинном коде виден вызов `printf@plt`.

- **GOT (Global Offset Table)** — таблица адресов внешних символов; записи могут заполняться загрузчиком во время выполнения.
- **PLT (Procedure Linkage Table)** — заглушки для вызова внешних функций через GOT.
- **Релокация (relocation)** — указание связчику/загрузчику подставить окончательный адрес символа; для вызовов в примере есть `JUMP_SLOT`.
- **Резолвер (`ld-linux`)** — находит реальный адрес внешней функции.

**Eager binding:** адреса разрешаются при загрузке, в том числе для функций, которые могут не понадобиться. **Lazy binding:** при первом вызове заглушка PLT ведёт к резолверу; он заполняет GOT, после чего последующие вызовы идут через готовый адрес. В заглушке переход идёт по записи GOT без отдельного условного ветвления. `-z now`/`LD_BIND_NOW` форсируют немедленное связывание.

**Практический смысл:** `ltrace` видит вызовы через PLT, но не обязательно статические или встроенные компилятором; повреждение GOT может перенаправить вызов. **RELRO** ограничивает возможность менять такие таблицы после загрузки. **ROP** — использование цепочки уже существующих фрагментов кода; в этой лекции достаточно знать назначение термина.

## 4. Почему переполнение угрожает управлению (слайды 23–28)

В иллюстративном 32-битном кадре **без канарейки** `buf[100]` начинается по смещению `-0x6c(%ebp)`, а адрес возврата находится по `+4(%ebp)`; расстояние между их началами — **112 байт** (100 байт буфера + выравнивание + сохранённые регистры). На слайде используется **116-байтовое** содержимое, затрагивающее четырёхбайтовый адрес возврата. Эти числа относятся **только к конкретной сборке**, а не ко всем функциям C.

**Stack canary** — контрольное значение между локальными данными и служебными полями кадра. Компилятор сохраняет его при входе и проверяет перед возвратом. Если оно повреждено, возможна остановка с сообщением `stack smashing detected`. **Канарейка обнаруживает определённые переполнения, но не предотвращает запись за границы.**

На лекции для демонстрации отключают проверки `-fno-stack-protector` и разрешают исполнение стека `-z execstack`. **Это настройки уязвимого учебного стенда, а не рекомендации для обычных программ.**

**Payload** — специально подготовленные входные данные. **NOP-sled** — серия инструкций «ничего не делать», расширяющая область возможного попадания; **shellcode** — небольшой внедрённый машинный код. В лекции эти понятия служат для демонстрации последствий повреждения адреса возврата.

## 5. Виртуальная память и страницы (слайды 29–35)

**Виртуальный адрес** — адрес, с которым работает программа (`&x`, адрес буфера, указатель `malloc`, адрес функции). Он не обязан совпадать с физическим адресом в RAM. **Каждый процесс имеет своё виртуальное адресное пространство**: одинаковый виртуальный адрес в двух процессах может отображаться на разные физические страницы.

**MMU (Memory Management Unit)** — аппаратный блок процессора, который переводит виртуальный адрес в физический через **таблицы страниц**. **Страница (page)** — блок памяти, в примере лекции **4 КиБ = 4096 байт**. Виртуальный адрес состоит из индексов для поиска записи таблицы и **смещения внутри страницы**, которое при переводе не меняется.

- Для страниц 4 КиБ смещение занимает **12 бит**; в описанной x86-64-схеме LA48: четыре уровня по 9 бит + 12 бит смещения. Вариант LA57: пять уровней.
- **TLB (Translation Lookaside Buffer)** — кеш недавних преобразований виртуальных адресов в физические.
- **Page fault** — событие при обращении к странице, требующее реакции ОС; может быть нормальным при подгрузке страницы (*demand paging*), а не только ошибкой.
- **Физический адрес** не всегда означает RAM: некоторые диапазоны относятся к **MMIO**, памяти устройств, ROM и зарезервированным областям. Их карту Linux показывает в `/proc/iomem`.

### Карта памяти процесса

В Linux файл `/proc/self/maps` показывает отображённые виртуальные области, их диапазоны, права и связь с файлами:

| Обозначение | Смысл |
|---|---|
| `[stack]` | Стек, кадры функций, аргументы запуска |
| `[heap]` | Область кучи |
| `libc.so.6` | Отображённая динамическая библиотека |
| `[vdso]`, `[vvar]` | Механизмы ускорения некоторых операций с участием ядра |
| `r--p`, `r-xp`, `rw-p` | Права: **R** чтение, **W** запись, **X** выполнение; `p` — private |

Участки `r-x` типичны для кода, `rw-` — для изменяемых данных. Страницы могут разделяться между процессами; **copy-on-write** позволяет делать частные копии при записи. `/proc` — виртуальная ФС: содержимое формируется ядром при чтении.

**Защита страниц:** CPU проверяет права при обращении. Недопустимое обращение может вызвать `SIGSEGV` (*Segmentation fault*; в примере shell показывает код `139 = 128 + 11`). Права можно менять через `mprotect()` — например, JIT-компилятор записывает машинный код в доступную для записи память и затем делает её исполняемой.

## 6. NX, PIE, ASLR: разные уровни защиты (слайды 36–38)

| Механизм | Расшифровка / суть |
|---|---|
| **NX** | *No-eXecute*: аппаратно запрещает исполнение на отмеченных страницах; обычно данные/стек неисполняемы. |
| **PIE** | *Position Independent Executable*: исполняемый файл не привязан к одному базовому адресу; позволяет рандомизировать и сам бинарник. |
| **ASLR** | *Address Space Layout Randomization*: при разных запусках меняется расположение стека, кучи, библиотек, `mmap`, а с PIE — и программы. |

**NX** препятствует выполнению кода из областей данных; **ASLR** усложняет угадывание адресов; **PIE** позволяет применить ASLR к исполняемому файлу. Это **не исправляет** ошибку переполнения. В лекции также отмечается политика **W∧X**: память не должна одновременно допускать запись и исполнение.

## 7. Системные вызовы и демонстрация (слайды 39–47)

**Системный вызов (syscall)** — передача управления от программы ядру ОС для выполнения системной операции. У него собственное соглашение о вызовах: отличные от обычного вызова функции инструкция, номер операции и регистры.

| Архитектура | Инструкция | Где номер вызова | Где результат |
|---|---|---|---|
| i386 | `int $0x80` | `eax` | `eax` |
| x86-64 | `syscall` | `eax` | `rax` |
| RISC-V 64 | `ecall` | `a7` | `a0` |

Например, `execve` **заменяет образ текущего процесса** другой программой — в отличие от `fork`, создающего процесс. Номера системных вызовов различаются по архитектурам (в лекции для `execve`: i386 — 11, x86-64 — 59, RISC-V 64 — 221). Они закрепляются ABI.

На слайдах 43–46 преподаватели демонстрируют подготовку короткого машинного фрагмента и изменение адреса возврата в специально уязвимой программе; при этом учитываются отсутствие `\0` в копируемых через `strcpy` байтах и адреса, наблюдаемые в `gdb`. **Учебный результат:** программа начинает делать то, чего не предполагалось её исходным кодом.

При включённом ASLR адреса меняются, поэтому показанная в лекции стратегия с угадыванием адреса ненадёжна. В качестве более сложных приёмов упоминаются **information leak** (утечка адресов), **ROP** (цепочки готовых участков кода) и **ret2libc** (использование функций libc). Для общего понимания достаточно различать саму уязвимость и механизмы, затрудняющие её эксплуатацию.

## 8. Итоговая карта лекции (слайды 48–50)

| Уровень | Что нужно помнить |
|---|---|
| Язык C | Запись за границы буфера — UB; `strcpy` не проверяет вместимость получателя |
| Вызов функций | `caller` / `callee`, calling convention, `call`, `ret`, стековый кадр |
| Двоичная совместимость | API ≠ ABI; регистры, размеры типов, выравнивание, соглашения различаются между платформами |
| Линковка | Внешние функции вызываются через PLT/GOT; адреса может разрешать загрузчик |
| Память процесса | Адреса виртуальные; MMU, таблицы страниц, TLB, права R/W/X |
| Защита | Канарейка — контроль стека; NX — запрет исполнения; PIE + ASLR — непредсказуемые адреса |
| ОС | Syscall — отдельный договор между программой и ядром |

**Главный вывод преподавателей:** атака переполнением — не самоцель, а пример, связывающий устройство функций, скомпилированного кода, динамических библиотек, виртуальной памяти и защит ОС.
