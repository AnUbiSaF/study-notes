# Лекция 03 — Исходный и исполняемый код

[[Лекции по программированию на C|← К лекциям]]

Теоретическая тема: [[Исходный и исполняемый код]]

## Этапы сборки C-программы

Одна команда:

```bash
gcc hello.c -o hello
```

на самом деле запускает несколько стадий:

```text
hello.c
  ↓ препроцессор
hello.i
  ↓ компилятор
hello.s
  ↓ ассемблер
hello.o
  ↓ линкер
hello
```

Формы кода:

- `.c` — исходный код;
- `.i` — препроцессированный код;
- `.s` — ассемблер;
- `.o` — объектный файл;
- executable — готовая программа.

Команды:

```bash
gcc -E hello.c -o hello.i   # только препроцессор
gcc -S hello.c -o hello.s   # до ассемблера
gcc -c hello.c -o hello.o   # до объектного файла
gcc hello.c -o hello        # полный путь + линковка
```

```bash
gcc --save-temps hello.c -o hello
```

сохраняет промежуточные `.i`, `.s`, `.o`.

## Ассемблер — минимум

Процессор исполняет машинный код. Ассемблер — человекочитаемые мнемоники машинных инструкций.

Пример AT&T-синтаксиса:

```asm
mov %eax, %ebx
```

означает:

```text
ebx = eax
```

Сначала источник, потом приёмник.

Базовые команды:

```text
mov   — копирование
add   — сложение
sub   — вычитание
cmp   — сравнение, выставляет флаги
jmp   — безусловный переход
call  — вызов функции
ret   — возврат
```

### Пример функции

```c
int sum(int a, int b) {
    return a + b;
}
```

Пример ассемблера:

```asm
mov %edi, %eax
add %esi, %eax
ret
```

Условно:

```text
edi = a
esi = b
eax = возвращаемое значение
```

### `if`

```c
if (x < 0)
    return -x;
```

может превратиться в:

```asm
cmp $0x0, %eax
jge .L1
neg %eax
.L1:
ret
```

`cmp` сравнивает, `jge` делает переход при `>=`.

То есть:

```text
if ≈ cmp + условный jump
```

## Стек — минимум

Стек нужен для данных вызова функции: локальных значений, сохранённых регистров, адреса возврата и т. п.

Пример:

```asm
mov %edi, -4(%rbp)
mov %esi, -8(%rbp)
```

`-4(%rbp)` и `-8(%rbp)` — места в текущем кадре стека относительно `rbp`.

Для летучки достаточно понимать:

```text
rbp — опорная точка кадра функции
-4(%rbp), -8(%rbp) — места внутри этого кадра
```

## Объектный файл `.o`

`.o` — не просто машинный код, а структурированный файл.

В нём есть:

- код по секциям;
- таблица символов;
- информация для линкера;
- метаданные.

В Linux основной формат — **ELF**.

### Главные секции ELF

```text
.text    — исполняемый код
.data    — инициализированные global/static
.bss     — неинициализированные или нулевые global/static
.rodata  — константы и строковые литералы
```

Пример:

```c
int x;
static int y;
```

→ `.bss`

```c
int x = 5;
static int y = 10;
```

→ `.data`

`.bss` не хранит в файле сами нулевые байты: сохраняется размер, а память обнуляется при запуске.

## Полезные утилиты

```bash
file hello.o
```

показывает тип файла, формат, архитектуру.

```bash
hexdump -C hello.o
```

показывает файл байт за байтом.

Первые байты ELF:

```text
7f 45 4c 46
```

— его сигнатура / magic number.

```bash
objdump -d hello.o
```

делает дизассемблирование:

```text
машинный код → ассемблер
```

## `nm` и символы

```bash
nm hello.o
```

может показать:

```text
0000000000000000 T main
                 U printf
```

Главные буквы:

```text
T → символ определён в .text
D → символ в .data
B → символ в .bss
R → символ в .rodata
U → используется, но здесь не определён
```

Заглавная буква обычно означает глобальный символ, строчная — локальный.

Число слева — позиция/смещение символа внутри соответствующей секции объектного файла.

## Declaration и definition

```c
void foo(void);
```

— **объявление**.

```c
void foo(void) {
    ...
}
```

— **определение**.

Объявления достаточно, чтобы компилятор разрешил вызов:

```c
void greet(void);

int main(void) {
    greet();
}
```

Но если тела `greet` нигде нет:

```text
compile → OK
link → undefined reference to `greet`
```

Компилятор знает сигнатуру, но линкер не находит реальное определение.

## Единица трансляции

**Translation unit**:

```text
один .c-файл + всё, что попало в него через #include
```

Каждый `.c` компилируется независимо.

Компилятор одного `.c` не знает содержимое других `.c`.

## `extern`

Пример:

### `a.c`

```c
int counter = 0;

void inc(void) {
    counter++;
}
```

### `b.c`

```c
extern int counter;
void inc(void);

int main(void) {
    inc();
    return counter;
}
```

`extern int counter;` означает:

```text
counter определён где-то в другом месте
```

Для функций отдельный `extern` обычно не нужен:

```c
void inc(void);
```

уже означает, что определение может находиться в другом файле.

`nm`:

```text
a.o:
B counter
T inc

b.o:
U counter
U inc
T main
```

Линкер связывает `U` из `b.o` с определениями из `a.o`.

## Раздельная компиляция и линковка

```bash
gcc -c a.c -o a.o
gcc -c b.c -o b.o
gcc a.o b.o -o prog
```

Если изменился только `b.c`:

```bash
gcc -c b.c -o b.o
gcc a.o b.o -o prog
```

`a.c` заново компилировать не нужно.

На этом основаны системы сборки вроде Makefile.

## Что делает линкер

На вход:

```text
несколько .o + библиотеки
```

На выход:

```text
один executable
```

Главные задачи:

1. **Symbol resolution** — найти определение для каждого `U`.
2. **Relocation** — подставить реальные адреса вместо временных заглушек.
3. **Объединить секции** — `.text` всех файлов вместе, `.data` вместе и т. д.

### Relocation

Если `main.o` вызывает функцию из `foo.o`, компилятор ещё не знает её окончательный адрес.

Поэтому в `.o` остаётся смысл:

```text
«сюда потом вставить адрес foo»
```

Линкер после объединения файлов подставляет реальный адрес.

## Ошибки линковки

### `undefined reference`

Символ используется, но нигде не определён.

Пример:

```c
void greet(void);

int main(void) {
    greet();
}
```

если определения `greet` нет:

```text
undefined reference to `greet`
```

### `multiple definition`

Один глобальный символ определён более одного раза.

Например, переменную определили в нескольких `.c` вместо использования `extern`.

## Почему `moin()` не заменяет `main()`

```c
int moin(void) {
    return 0;
}
```

`moin` — обычная корректная функция.

Но runtime ожидает функцию именно с именем:

```text
main
```

Поэтому при сборке executable:

```text
undefined reference to `main`
```

## Что происходит до `main`

`main` — не первая исполняемая инструкция программы.

Упрощённо:

```text
ядро
→ _start
→ runtime C
→ main(...)
→ exit(...)
```

Глубоко знать `_start`, `crt1.o`, `__libc_start_main` не нужно; важно понимать, что `main` вызывается рантаймом.

## `main`, `argc`, `argv`

Допустимые формы:

```c
int main(void)
```

или:

```c
int main(int argc, char **argv)
```

Возвращаемое значение `main` — код завершения процесса.

Посмотреть:

```bash
./hello
echo $?
```

Пример:

```bash
./prog one two
```

даёт:

```text
argc = 3

argv[0] = "./prog"
argv[1] = "one"
argv[2] = "two"
argv[3] = NULL
```

Важно:

```text
argv[argc] == NULL
```

## `stdin`, `stdout`, `stderr`

Стандартные потоки:

```text
0 → stdin  → обычный ввод
1 → stdout → обычный вывод
2 → stderr → ошибки
```

Пример:

```c
printf("result = 42\n");           // stdout
fprintf(stderr, "warning!\n");     // stderr
```

Разделение `stdout` и `stderr` позволяет перенаправлять обычные данные и ошибки отдельно.

## Перенаправление потоков

```bash
prog > out.txt
```

`stdout` → `out.txt`

```bash
prog < in.txt
```

`stdin` ← `in.txt`

```bash
prog 2> err.txt
```

`stderr` → `err.txt`

```bash
prog1 | prog2
```

`stdout` первой программы → `stdin` второй.

Программа сама не обязана знать о перенаправлении — это настраивает shell.

## Статическая и динамическая линковка

### Статическая `.a`

Код библиотеки копируется внутрь executable.

```text
+ программа самодостаточна
- executable больше
```

```bash
gcc -static prog.c -o prog
```

`.a` — архив объектных файлов.

### Динамическая `.so`

В executable остаётся ссылка на библиотеку, а сама `.so` загружается при запуске.

```text
+ executable меньше
+ библиотека может переиспользоваться
- библиотека должна быть установлена на машине
```

```bash
ldd hello
```

показывает зависимости от динамических `.so`.

Если нужной `.so` нет, ошибка может возникнуть уже при запуске:

```text
error while loading shared libraries
```

## Предупреждения компилятора

Рекомендуемая сборка:

```bash
gcc -Wall -Wextra -Werror -pedantic prog.c -o prog
```

- `-Wall` — основной набор warnings;
- `-Wextra` — дополнительные warnings;
- `-pedantic` / `-Wpedantic` — предупреждать о нестандартных расширениях;
- `-Werror` — warning становится compile error.

## Оптимизации

```text
-O0   — без оптимизаций
-O1   — базовые
-O2   — сильнее
-O3   — агрессивные
-Os   — оптимизация размера файла
```

Примеры оптимизаций со слайдов:

- раскрытие циклов;
- замена инструкций;
- инлайнинг;
- векторизация/SSE.

Для отладки удобно `-O0`, для обычной оптимизированной сборки используют более высокие уровни.

nm:
T → определено в .text

declaration ≠ definition

.h нужен компилятору

extern → определение переменной находится где-то ещё

линкер:
